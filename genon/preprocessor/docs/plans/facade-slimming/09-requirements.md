# 신규 문서 처리 요건 14건

문서 검색 시스템에 새로 들어올 문서들의 처리 요건입니다. 각 요건을 읽고
전처리기 파일 두 개(파서·청커)에서 **어디를 어떻게 고칠지** 판단해 주세요.

## 요건 1. 문서관리시스템이 내려주는 파일에 버전 꼬리표가 붙어 접수가 안 됨

**고객사 상황**
지방은행 여신·수신 업무 매뉴얼을 사내 EDMS에서 일괄로 내려받아 검색 시스템에 넣습니다. EDMS가 버전 관리를 하느라 내려받은 파일 이름 끝에 리비전 꼬리표를 붙여서 내려줍니다. 지금은 담당자가 손으로 이름을 고쳐 올리는데 월 2천 건이라 감당이 안 됩니다.

**원본**
```
여신심사기준_2026개정.pdf.v3
수신상품안내_영업점용.docx.v12
외환업무매뉴얼.hwp.r2
개인신용평가_운영지침.pdf.d1
```

**요구사항**
- 꼬리표가 붙은 파일도 원래 문서 종류대로 처리되어야 합니다.
- 이름을 손으로 고치는 작업이 없어야 합니다. EDMS는 저희가 손댈 수 없습니다.
- 꼬리표 종류는 앞으로 늘어납니다(`.v`, `.r`에 이어 최근 `.d`가 나왔습니다). 그때마다 개발 요청을 넣고 재배포하는 건 곤란합니다.
- 검색 결과 화면에 나오는 문서 이름에는 꼬리표가 안 보였으면 합니다.

**완료 판정 기준**
- 위 4개 파일을 그대로 넣었을 때, 꼬리표를 뗀 같은 파일과 청크 수·본문이 동일하게 나온다.
- 새 꼬리표 한 종류를 추가하는 데 코드 수정과 재배포가 필요 없다.
- 결과에 실리는 문서명이 `여신심사기준_2026개정.pdf` 형태다.

## 요건 2. FAQ 엑셀 — 머리글이 6행부터, 비공개 행과 내부용 열이 섞여 있음

**고객사 상황**
카드사 고객센터 FAQ 원장을 엑셀 한 권으로 관리합니다. 시트 맨 위 5줄은 담당자 검토 메모라 실제 표 머리글은 6행입니다. "노출여부"가 N인 항목은 아직 오픈 전이라 검색에 나오면 안 되고, "내부 담당자"·"개발계 URL"은 검색에 걸리면 안 되지만 운영에서 봐야 해서 저장은 되어야 합니다.

**원본** (시트 `공통_FAQ`)
```
[1행] 검토 및 요청사항: 3분기 개정분 반영 요청
[2행] 예상 파일명: card_faq_20260901_full_001.xlsx
[3~5행] (빈 행 / 임베딩컬럼여부 표시)
[6행] ID | 회사명 | 분류 | 질문 | 답변 | 내부 담당자 | 개발계 URL | 최종수정일 | 노출여부
[7행] cf_0012 | 카드 | 카드발급 | 카드 재발급은 어떻게 하나요? | 앱 > 카드 > 재발급... | 김OO | http://dev.example/... | 2026-08-14 | Y
[8행] cf_0013 | 카드 | 결제  | 결제일 변경이 되나요?      | 결제일은 매월...        | 박OO | http://dev.example/... | 2026-08-20 | N
```

**요구사항**
- 맨 위 메모 5줄을 표의 일부로 읽으면 안 됩니다.
- 노출여부가 N인 FAQ는 검색에 절대 나오면 안 됩니다.
- 내부 담당자·개발계 URL은 검색되는 본문에는 안 들어가되 저장 행에는 남아야 합니다.
- 최종수정일은 운영 DB에서 숫자 8자리(20260814)로 씁니다.
- 답변이 길어 여러 조각으로 잘리더라도, 각 조각이 어떤 질문에 대한 답인지 알 수 있어야 합니다.

**완료 판정 기준**
- 100행 샘플에서 노출여부 N인 12건이 결과에 0건.
- 저장 행에는 담당자·개발계 URL 값이 채워져 있고, 검색 본문 텍스트에는 그 문자열이 없다.
- 최종수정일이 `20260814` 형태의 정수로 저장된다.
- 답변이 길어 2조각으로 잘린 항목의 두 조각 모두가 질문 문장으로 시작한다.

## 요건 3. 회의 녹취 — 어느 회의 몇 번째 안건인지 알 수 있어야 함

**고객사 상황**
광역시 산하 공공기관 심의위원회 녹취를 검색 대상으로 넣습니다. 받아쓰기 자체는 잘 되는데, 검색 결과가 "…그 부분은 다음 회기로 넘기겠습니다" 같은 문장 토막이라 어느 회의 어느 안건인지 알 수가 없습니다. 회의명·일자·안건은 파일명에 규칙적으로 들어 있습니다.

**원본**
```
20260415_제3차_도시계획위원회_제2호안건_원본.m4a
20260415_제3차_도시계획위원회_제5호안건_원본.mp3
20260602_제4차_공유재산심의회_제1호안건_원본.wav
```

**요구사항**
- 검색 결과 한 줄만 봐도 회의명·차수·일자·안건 번호를 알 수 있어야 합니다.
- 회의명/일자/안건은 목록 화면에서 조건 검색(예: 도시계획위원회 2026년 4월)에 쓸 예정이라 값으로도 따로 있어야 합니다.
- 긴 회의는 여러 조각으로 나뉘는데, 화면에서 발언 순서대로 붙여 읽을 수 있어야 합니다.
- 파일명 규칙이 2027년 1월부터 바뀝니다.

**완료 판정 기준**
- 위 3개 파일 결과의 모든 조각이 회의명·일자·안건으로 시작한다.
- 회의명·일자(정수 8자리)·안건번호가 각각 별도 값으로 저장된다.
- 같은 파일에서 나온 조각을 저장 순서로 정렬하면 녹취 시간 순서와 일치한다.
- 파일명 규칙이 바뀌어도 코드 수정·재배포 없이 반영된다.

## 요건 4. 리서치 통계표 엑셀 — 머리글이 2층, 한 시트에 표 여러 개, 일부는 세로형

**고객사 상황**
증권사 리서치센터가 산업분석 보고서 부록 통계를 엑셀로 관리합니다. 한 시트에 표가 2~4개씩 빈 행으로만 구분되어 들어 있고, 머리글이 2단(위는 연도, 아래는 분기)인 표가 섞여 있습니다. 어떤 표는 아예 세로형이라 왼쪽 열이 항목명, 오른쪽 한 열이 값입니다. 지금은 시트가 통째로 한 덩어리라 "2025년 3분기 반도체 수출액" 같은 질문에 답을 못 합니다.

**원본** (시트 `수출입`)
```
[가로형, 2단 머리글]
                  2025년              2026년
             1Q    2Q    3Q     1Q    2Q
반도체       412   455   501    530   548
디스플레이   118   120   115    109   102

(빈 행)

[세로형]
조사기준일    2026-06-30
작성부서      리서치센터 산업분석팀
단위          억 달러
```

**요구사항**
- "2025년 3분기 반도체"로 검색하면 그 숫자가 든 조각이 나와야 합니다. 연도와 분기가 따로 놀면 안 됩니다.
- 한 시트에 있는 표들이 서로 섞이면 안 됩니다. 표마다 별개로 다뤄져야 합니다.
- 세로형 표는 항목-값 쌍으로 읽혀야 하고, 같은 시트의 다른 표 조각에 조사기준일·단위가 함께 붙어야 합니다. 숫자만 있고 단위가 없으면 현업이 쓸 수 없습니다.
- 행이 많은 표는 잘려도 되지만, 잘린 조각마다 머리글이 다시 붙어야 합니다.

**완료 판정 기준**
- 예시 시트에서 표 2개가 각각 분리되어 나온다.
- "2025년 3분기 반도체"에 해당하는 조각에 값 501이 들어 있다.
- 가로형 표에서 나온 모든 조각에 "억 달러"와 조사기준일 2026-06-30이 포함된다.
- 60행짜리 표를 잘랐을 때 모든 조각의 첫 줄이 머리글이다.

## 요건 5. 표 자동 설명이 업무에서 못 쓰는 문장으로 나옴

**고객사 상황**
저축은행 상품팀입니다. 예·적금 금리표와 수수료표가 들어간 상품설명서를 검색에 넣는데, 자동으로 붙는 표 설명이 "이 표는 다양한 금리 정보를 보여줍니다" 수준이거나, 표에 없는 숫자를 만들어 낸 적이 있습니다. 감사에서 지적을 받은 뒤로 상품팀이 자동 설명 자체를 신뢰하지 않습니다.

**원본** (상품설명서 PDF 안의 표)
```
[정기예금 기본금리]  (기준일: 2026.07.01, 연 %, 세전)
가입기간      6개월   12개월   24개월
개인           2.85    3.10     3.20
법인           2.70    2.95     3.05
```

**요구사항**
- 표 설명에 상품명·기준일·단위(연 %, 세전 여부)가 반드시 들어가야 합니다. 셋 중 하나라도 빠지면 그 설명은 안 붙이는 편이 낫습니다.
- 표에 없는 숫자나 조건(우대금리, 중도해지 등)을 지어내면 안 됩니다.
- 설명은 두 문장 이내. 표 안 숫자를 그대로 다시 읊는 건 필요 없습니다. 숫자는 표 자체로 검색됩니다.
- 상품팀이 문구 기준을 계속 다듬을 예정이라, 기준을 바꿀 때마다 개발 배포가 필요하면 안 됩니다.
- 설명 생성이 실패하거나 기준 미달이어도 표 자체는 들어가야 합니다. 문서 전체가 실패하면 안 됩니다.

**완료 판정 기준**
- 샘플 표 20개에서 생성된 설명 전부가 상품명·기준일·단위를 포함한다.
- 기준 미달 설명은 결과에 실리지 않고, 그 경우에도 표 본문은 남는다.
- 문구 기준만 바꿔 재실행하면 설명 내용이 바뀐다(코드 수정 없음).
- 설명에 표에 없는 숫자가 들어간 건이 20건 중 0건.

## 요건 6. 같은 서식인데 관계사마다 규칙이 다름

**고객사 상황**
금융지주입니다. 은행·카드·보험·증권 4개 관계사가 같은 상품안내 서식을 쓰지만 검색 시스템은 지주 통합으로 하나입니다. 관계사마다 마스킹 기준이 다르고(보험은 설계사 이름까지 가려야 하고 은행은 안 가림), 결과에 붙는 안내 문구와 조각 길이 기준도 다릅니다. 지금은 관계사별로 전처리기를 4벌 따로 띄워 놨는데 문구 하나 바꾸는 데 4번 배포해야 합니다.

**원본** (같은 서식, 관계사만 다름)
```
[문서 머리] OO생명 / 상품안내 / 2026-05-02 / 담당 설계사: 홍길동 (010-0000-0000)
[문서 머리] OO은행 / 상품안내 / 2026-05-02 / 담당 창구: 강남지점 (02-0000-0000)
```

**요구사항**
- 관계사 구분은 문서 머리에 들어 있습니다. 파일명이나 폴더로는 구분이 안 됩니다(같은 폴더에 섞여 들어옵니다).
- 보험은 설계사 이름과 연락처를 모두 가리고, 은행·카드는 지점명은 남기고 연락처만 가리고, 증권은 둘 다 남깁니다.
- 관계사별 안내 문구가 조각 앞에 붙어야 합니다.
- 내년에 캐피탈이 추가됩니다. 관계사 규칙이 늘거나 바뀔 때 다른 관계사 결과가 영향을 받으면 안 됩니다.
- 전처리기는 한 벌로 운영하고 싶습니다.

**완료 판정 기준**
- 4개 관계사 문서를 한 번에 넣어 각각 다른 마스킹·문구가 적용된다.
- 보험 문서 결과 어디에도 "홍길동"과 "010-"이 없다.
- 은행 문서에서 "강남지점"은 남고 전화번호만 가려진다.
- 캐피탈 규칙을 추가한 뒤 재실행해도 기존 4개 관계사의 결과가 이전과 동일하다.

## 요건 7. 표가 잘려 답이 안 나옴 — 행 단위와 표 전체를 같이 갖고 싶음

**고객사 상황**
손해보험사입니다. 보장내용 비교표가 30~80행인데, 조각을 크게 잡으면 "상해입원일당 자기부담금" 같이 콕 집은 질문에 표 전체가 걸려 답이 묻히고, 작게 잡으면 "이 상품 보장 전체를 요약해줘"에 답을 못 합니다. 현업은 둘 다 되기를 원합니다.

**원본**
```
[표] 무배당 OO상해보험 보장내용
담보명          가입금액     지급사유                   자기부담금
상해사망        1억원        상해로 사망한 경우          -
상해입원일당    3만원/일     상해로 4일 이상 입원 시     3일
질병수술비      50만원       약관상 수술을 받은 경우      -
```

**요구사항**
- 담보 하나만 물으면 그 행이 걸려야 합니다.
- 상품 전체 보장을 물으면 표 전체가 한 덩어리로 걸려야 합니다.
- 같은 표가 두 벌로 저장되므로, 화면에서 같은 내용이 중복 노출되지 않도록 어느 쪽인지 구분이 되어야 합니다.
- 행 단위 조각도 표 제목과 머리글을 갖고 있어야 합니다. 맥락 없이 "3일"만 있으면 못 씁니다.
- 원문의 담보 나열 순서가 결과에서 유지되어야 합니다.

**완료 판정 기준**
- 예시 표 하나에서 행 단위 3건과 표 전체 1건이 함께 저장된다.
- 두 종류가 저장 행에서 구분된다.
- 행 단위 조각 각각에 표 제목과 머리글이 들어 있다.
- 행 단위 조각을 저장 순서로 정렬하면 원문 순서와 같다.
- 표 전체 조각이 길이 제한 때문에 통째로 사라지거나 잘려 나가지 않는다.

## 요건 8. 상품 API 응답 JSON — 중첩이 깊고 한 파일에 종류가 섞여 있음

**고객사 상황**
생명보험사 디지털본부입니다. 상품 정보를 사내 API에서 하루 한 번 통째로 내려받아 JSON 한 파일로 받습니다. 한 파일 안에 상품·특약·공지가 섞여 있고, 상품 안에는 보장항목 배열이, 보장항목 안에 다시 지급사유 배열이 들어 있습니다. 지금은 파일 전체가 한 덩어리 텍스트로 들어가 검색이 안 됩니다.

**원본**
```json
{"batchDate":"20260901","items":[
 {"type":"product","code":"L2026-014","name":"무배당 든든한종신보험",
  "coverages":[{"name":"주계약","amount":"1억원",
                "payReasons":[{"case":"사망","rate":"100%"},{"case":"고도장해","rate":"80%"}]},
               {"name":"재해사망특약","amount":"5천만원",
                "payReasons":[{"case":"재해사망","rate":"100%"}]}]},
 {"type":"rider","code":"R-221","parentCode":"L2026-014","name":"입원일당특약","desc":"..."},
 {"type":"notice","noticeId":"N-3391","title":"9월 상품 개정 안내","body":"..."}]}
```

**요구사항**
- 상품·특약·공지는 성격이 달라 검색 결과에서 구분되어야 하고, 저장되는 항목도 서로 다릅니다.
- 지급사유까지 검색이 되어야 합니다. "고도장해 지급률"로 물으면 해당 상품이 나와야 합니다.
- 특약은 어느 상품에 딸린 것인지 알 수 있어야 합니다.
- 배열 깊이는 더 늘 수 있다고 API 팀이 얘기했습니다. 내년에는 같은 내용을 XML로도 내려줄 예정입니다.
- 한 종류(예: 공지)에서 오류가 나도 나머지는 들어가야 합니다. 하루치가 통째로 실패하면 운영에서 감당이 안 됩니다.
- 매일 전량을 다시 넣으므로 같은 코드의 상품은 덮어쓸 수 있게 식별값이 있어야 합니다.

**완료 판정 기준**
- 예시 파일에서 상품 1건·특약 1건·공지 1건이 서로 다른 종류로 저장된다.
- "고도장해"로 검색하면 해당 상품 조각이 걸린다.
- 특약 저장 행에 상품코드 `L2026-014`가 들어 있다.
- 공지 항목에 깨진 값을 넣은 파일에서도 상품·특약은 정상 저장되고 실패 건수가 결과에 보고된다.
- 같은 파일을 두 번 넣어도 상품 코드별로 1건씩만 남는다.

## 요건 9. 이메일 아카이브 — 스레드·인용문·첨부가 뒤엉켜 있음

**고객사 상황**
공기업 감사실입니다. 계약 관련 메일함을 통째로 내보내 검색 대상으로 만들려 합니다. 메일 1건이 파일 1개(.eml, 일부 .msg)입니다. 답장이 오갈수록 이전 메일 전문이 인용으로 계속 따라붙어 같은 문장이 수십 번 반복되고, 서명·면책 문구가 매 메일에 붙습니다. 첨부(계약서 PDF, 산출내역 엑셀, 압축된 도면 묶음)가 본문보다 중요한 경우가 많습니다.

**원본**
```
From: 담당자A <a@example.co.kr>
To: 담당자B <b@example.co.kr>
Sent: 2026-03-11 14:02
Subject: RE: RE: [계약] OO청사 공사 변경계약 검토 요청
Attachments: 변경계약서_v3.pdf; 산출내역서.xlsx; 도면묶음.zip

검토 결과 회신드립니다. 3항은 수정이 필요합니다.

> -----Original Message-----
> Subject: RE: [계약] OO청사 공사 변경계약 검토 요청
> 첨부와 같이 검토 요청드립니다. ...
(이하 인용 40줄)
--
담당자A / 계약팀 / 02-000-0000
본 메일은 수신자 외 열람을 금합니다. 잘못 수신하셨다면 삭제하여 주시기 바랍니다.
```

**요구사항**
- 인용된 이전 메일 본문이 중복 저장되면 안 됩니다. 새로 쓴 부분만 검색되면 됩니다.
- 서명·면책 문구는 검색에서 빠져야 합니다.
- 보낸사람·받는사람·보낸시각·제목이 값으로 남아야 하고, 제목의 RE:/FW: 반복은 정리되어야 합니다.
- 첨부 내용도 검색되어야 하고, 어느 메일에 딸린 첨부인지 알 수 있어야 합니다. 압축 첨부 안의 파일도 마찬가지입니다.
- 같은 스레드에 속한 메일들을 시간순으로 묶어 볼 수 있어야 합니다.
- 열 수 없는 첨부(암호가 걸린 파일 등)가 있어도 메일 본문은 들어가야 합니다.

**완료 판정 기준**
- 예시 메일 결과에 인용 40줄이 없다.
- 면책 문구가 결과 어디에도 없다.
- 제목 값이 `[계약] OO청사 공사 변경계약 검토 요청`이다.
- 첨부 3개(압축 안 파일 포함)가 각각 저장되고 모두 원본 메일 식별값을 갖는다.
- 암호 걸린 첨부가 있는 메일에서 본문과 나머지 첨부는 정상 저장되고, 실패한 첨부가 결과에 보고된다.
- 같은 스레드 5건을 보낸시각 순으로 정렬할 수 있다.

## 요건 10. 대외계 전문 원장 — 고정폭 텍스트에 코드값만 들어 있음

**고객사 상황**
제2금융권입니다. 심사·승인 이력을 대외계에서 고정폭 텍스트로 떨궈 줍니다. 구분자가 없고 자리수로 필드가 갈립니다. 첫 3자리가 레코드 종류이고 종류마다 그 뒤 레이아웃이 완전히 다릅니다. 값은 대부분 코드라 사람이 읽을 수 없고, 코드-한글 대응표는 별도 엑셀로 관리합니다. 현업은 "2026년 3월에 소득증빙 부족으로 부결된 건" 같은 질문을 하고 싶어 합니다.

**원본** (`APPR_20260311.txt`, 한 줄 200바이트 고정)
```
H0120260311APPR_BATCH_001                                        0000234
D01A0000012320260311093015030CR02  0450000000Y004
D01A0000012420260311093211010CR07  0120000000N012
T0100000234000000221000000013
```
코드표 `codebook.xlsx`: `004=소득증빙 부족`, `012=신용등급 미달`, `CR02=신용대출`, `CR07=주택담보`

**요구사항**
- 헤더(H)·명세(D)·트레일러(T)를 구분해 명세 행만 검색 대상이면 됩니다.
- 자리수 정의는 대외계 인터페이스 정의서에 있고, 내년 1월 개정 때 필드가 2개 늘어납니다. 그때 코드를 다시 짜야 하면 곤란합니다.
- 코드값은 한글로 바뀌어 저장·검색되어야 합니다. "004"가 아니라 "소득증빙 부족"입니다.
- 코드표는 분기마다 갱신됩니다. 갱신에 전처리기 재배포가 필요 없으면 좋겠습니다.
- 금액·일자는 숫자/날짜로 조건 검색이 되어야 합니다.
- 트레일러의 건수와 실제 명세 건수가 다르면 그 파일은 아예 받지 말아야 합니다. 원장이라 부분 적재가 더 위험합니다.

**완료 판정 기준**
- 예시 파일에서 명세 2건만 저장되고 헤더·트레일러는 저장되지 않는다.
- 저장된 값에 "소득증빙 부족", "신용대출"이 들어 있다.
- 승인일자가 `20260311`, 금액이 `450000000` 형태의 숫자로 저장된다.
- 코드표 엑셀만 교체하고 재실행하면 한글 표기가 바뀐다.
- 트레일러 건수를 234에서 235로 바꾼 파일은 처리가 거부되고 사유가 남는다.
- 필드 2개가 추가된 신규 레이아웃이 코드 수정 없이 반영된다.

## 요건 11. 규정집 엑셀 — 시트마다 형식이 다르고 개정 이력이 함께 들어 있음

**고객사 상황**
대형 제조사 준법지원팀입니다. 사내 규정을 엑셀 한 권으로 관리합니다. 1번 시트는 표지, 2번은 개정 이력, 3번부터가 규정 본문인데 시트마다 서식이 다릅니다. 어떤 시트는 조/항/호가 열로 나뉘어 있고 어떤 시트는 한 셀에 조문 전체가 들어 있습니다. 마지막 시트는 용어 정의표입니다. 현업은 "현행 규정만" 검색되기를 원하는데, 폐지·개정 전 조문이 본문 시트에 회색 글씨로 그대로 남아 있습니다.

**원본**
```
[시트 표지]         사내규정집 v18 / 시행일 2026-07-01 / 준법지원팀

[시트 개정이력]     차수 | 시행일     | 개정 조문      | 사유
                    18   | 2026-07-01 | 제12조, 제31조 | 내부통제 강화
                    17   | 2025-11-01 | 제7조          | 법령 개정 반영

[시트 인사규정]     조 | 항 | 호 | 내용              | 상태
                    12 | 1  | -  | 임직원은 ...      | 현행
                    12 | 1  | -  | (구) 임직원은 ... | 폐지

[시트 정보보호규정] 조문전체
                    제5조(비밀유지) ① 임직원은 ... ② ...

[시트 용어정의]     용어 | 정의
```

**요구사항**
- 표지·개정이력·용어정의 시트는 규정 본문과 성격이 다릅니다. 조문처럼 검색되면 안 됩니다.
- 폐지·개정 전 조문은 검색에 나오면 안 됩니다. 다만 감사 대응용으로 저장은 되어야 합니다.
- 조문이 열로 나뉜 시트와 한 셀에 통으로 들어간 시트가 같은 형태로 검색되어야 합니다. "제12조 제1항"으로 물으면 두 시트 모두 같은 방식으로 나와야 합니다.
- 각 조문이 몇 차 개정분이고 시행일이 언제인지 알 수 있어야 합니다. 그 정보는 개정이력 시트에 있습니다.
- 용어 정의는 조문 검색 결과에 참고로 붙으면 좋겠습니다.
- 시트가 연 3~4개씩 늘어납니다. 시트가 추가될 때마다 개발 요청을 넣고 싶지 않습니다.

**완료 판정 기준**
- 예시 엑셀에서 규정 본문 시트만 조문으로 저장된다.
- 상태가 "폐지"인 조문이 검색 결과에 0건이고, 저장 행에는 존재하며 구분값을 갖는다.
- 두 형식 시트 모두에서 "제12조 제1항", "제5조 제1항"이 조·항 단위로 특정된다.
- 각 조문 행에 개정차수 18, 시행일 20260701이 붙는다.
- 시트를 하나 추가한 파일이 코드 수정 없이 처리된다.

## 요건 12. 대용량 문서 — 시간 안에 못 끝내면 절반이라도 달라

**고객사 상황**
공공기관 사업관리부입니다. 입찰 제안서·과업지시서가 300~800쪽이고 스캔본이 섞여 있습니다. 야간 일괄 적재 창이 4시간인데 한 건이 40분 넘게 잡아먹고, 중간에 실패하면 그 문서는 통째로 빠진 채 아침을 맞습니다. 담당자 입장은 "다 안 되면 앞부분이라도 들어가 있어야 한다"입니다.

**원본**
스캔 PDF 620쪽(본문 500쪽 + 부록 도면 80쪽 + 서식 40쪽), 파일 250MB.

**요구사항**
- 문서 1건당 처리 시간 상한을 운영에서 정할 수 있어야 합니다.
- 상한을 넘으면 그 시점까지 처리된 부분은 저장되고, 어디까지 됐는지 남아야 합니다. 전부 버리면 안 됩니다.
- 부분만 들어간 문서를 담당자가 알 수 있어야 합니다. 운영 화면에 목록으로 뽑을 예정입니다.
- 다시 돌릴 때 이미 끝난 앞부분을 처음부터 다시 하지 않으면 좋겠습니다.
- 부록 도면·서식은 검색 가치가 낮으니, 시간이 모자라면 본문이 먼저 처리되어야 합니다.
- 동시에 여러 건이 들어와도 한 건이 느리다고 다른 건이 밀리면 안 됩니다.

**완료 판정 기준**
- 상한을 10분으로 두고 620쪽 문서를 넣으면 10분 시점에 응답이 오고, 그때까지 처리된 쪽의 조각이 저장된다.
- 결과에 "미완료" 표시와 마지막으로 처리한 쪽 번호가 남는다.
- 같은 문서를 다시 넣으면 첫 실행보다 짧은 시간에 끝난다.
- 620쪽 문서와 10쪽 문서를 동시에 넣었을 때 10쪽 문서가 1분 안에 끝난다.

## 요건 13. 마크다운 문서 — 제목을 `#` 으로 안 쓰고 자체 기호로 표시함

**고객사 상황**
제조사 기술문서팀입니다. 사내 위키와 설비 매뉴얼을 마크다운으로 내보내는데, 작성자들이 `#` 문법을 거의 안 쓰고 사내 서식 관행대로 기호를 붙여 계층을 표시합니다. 부서마다 쓰는 기호도 다릅니다. 지금은 문서 전체가 제목 없는 한 덩어리로 들어가서, 검색 결과에 "어느 절의 내용인지"가 안 나옵니다. 200쪽짜리 설비 매뉴얼에서 문장 하나만 나오면 현업이 못 씁니다.

**원본** (설비팀 문서)
```
【1. 장비 개요】
본 장비는 ...

  ■ 1.1 주요 사양
  전압: 220V

  ■ 1.2 설치 조건
  □ 온도: 10~35도
  □ 습도: 40~60%

【2. 점검 절차】
==========
2.1 일상점검
----------
매일 시작 전 ...
```
(품질팀 문서는 `【 】` 대신 `<<1. 개요>>`, `■` 대신 `▶` 를 씁니다.)

**요구사항**
- 위 기호 줄들이 제목으로 인식되어 계층이 잡혀야 합니다. `【 】` 가 큰 제목, `■` 가 중간 제목, `□` 가 작은 제목입니다.
- 밑줄 방식(`====`, `----`)으로 표시된 제목도 같이 인식되어야 합니다.
- 부서마다 기호가 다르므로 문서 종류별로 다른 규칙을 줄 수 있어야 합니다.
- 코드 블록(``` 안)이나 표 안에 같은 기호가 있으면 제목으로 잡으면 안 됩니다.
- 검색 결과 조각에 "1. 장비 개요 > 1.2 설치 조건" 같은 경로가 붙어야 합니다.
- 기호 규칙은 부서가 늘 때마다 추가됩니다. 그때마다 배포하면 곤란합니다.

**완료 판정 기준**
- 예시 문서에서 제목 6개(【1】【2】 ■1.1 ■1.2 □온도 □습도 상당)가 계층으로 잡힌다.
- 검색 조각에 상위 제목 경로가 붙는다.
- 코드 블록 안의 `■` 로 시작하는 줄이 제목으로 잡히지 않는다.
- 품질팀 기호(`<<>>`, `▶`)를 추가하는 데 코드 수정이 필요 없다.

## 요건 14. 문서 종류마다 켜고 끌 기능이 다름 — 설정을 코드에서 정하고 싶음

**고객사 상황**
통신사 CX본부입니다. 한 전처리기로 20종 가까운 문서를 처리하는데, 문서마다 필요한 기능이 다릅니다. 계약서·약관은 표 설명이 검색 품질에 크게 도움이 되지만, 보도자료·공지사항은 표가 거의 없는데도 설명 생성이 돌아 시간과 비용만 씁니다. 이미지 설명은 매뉴얼에만 필요하고, OCR 은 스캔 문서에만 필요합니다. 지금은 이런 항목이 전부 설정 파일 한 벌에 전역으로 들어 있어 문서 종류별로 끄고 켤 수가 없습니다. 설정 파일을 문서 종류 수만큼 만들어 전처리기를 여러 벌 띄우는 것도 해 봤는데 운영이 감당을 못 했습니다.

**원본**
같은 전처리기로 들어오는 문서들입니다.
```
계약서.pdf        (doc_type=contract)   표 설명 필요, 이미지 설명 불필요, OCR 필요
보도자료.docx     (doc_type=press)      표 설명 불필요, 이미지 설명 불필요, 청크 크기 작게
설비매뉴얼.pdf    (doc_type=manual)     표 설명 필요, 이미지 설명 필요, 청크 크기 크게
민원접수.json     (doc_type=vo c)       모두 불필요, 정제 규칙만 다르게
```

**요구사항**
- 문서 종류에 따라 자동 설명(표·이미지·요약), OCR, 청크 크기, 정제 규칙을 켜고 끌 수 있어야 합니다.
- 특정 값 몇 개가 아니라 **설정 파일에 있는 항목이면 무엇이든** 이렇게 조정할 수 있어야 합니다. 지금 필요한 건 표 설명 끄기지만, 다음 달에 무엇이 필요할지 모릅니다.
- 요청할 때 값을 실어 보내는 방식(호출 쪽에서 지정)도 함께 되면 좋겠습니다. 같은 문서를 재처리할 때 일부만 다르게 돌리는 경우가 있습니다.
- 문서 A 를 처리하며 바꾼 설정이 동시에 처리 중인 문서 B 에 영향을 주면 절대 안 됩니다. 실제로 다른 시스템에서 이런 사고가 있었습니다.
- 어떤 문서가 어떤 설정으로 처리됐는지 결과에 남아야 합니다. 검색 품질 문제가 생겼을 때 원인을 찾아야 합니다.
- 전처리기는 한 벌로 운영합니다.

**완료 판정 기준**
- `doc_type=press` 문서는 표 설명이 생성되지 않고, `doc_type=contract` 는 생성된다. 설정 파일은 한 벌이다.
- 표 설명 외에 다른 항목(예: 청크 크기, OCR 사용 여부)도 같은 방식으로 문서 종류별로 달라진다.
- 두 종류를 동시에 처리해도 서로의 설정이 섞이지 않는다.
- 결과에 그 문서에 적용된 설정 값이 기록된다.
